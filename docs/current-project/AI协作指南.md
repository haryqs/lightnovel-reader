## 已做出的技术决策（不再争论）

### 框架：Tauri v2
- 理由：跨平台（Win/Mac/Linux + iOS/Android），原生 WebView，打包 < 10MB
- 不选 Electron：体积大（>100MB），内存占用高
- 不选纯 Web：违反离线优先，且无法访问本地文件系统

### 渲染策略：Rust 解析 + TS 分页（非 epubjs，非 foliate-js）
- 理由：见 `1_技术决策_选型推导.md`
- 核心：EPUB 解析在 Rust 端完成，前端只做 CSS Columns 分页
- 不选 epubjs：失维护，对旧 EPUB 无清洗能力
- 不选 foliate-js：API 不稳定（无 npm 发布），同样不洗 HTML
- 不选 Readium：需要 Swift/Kotlin/TS 三套代码
- 不选服务器方案：违反离线优先

### 前端：纯 TypeScript + Vite（无框架）
- 理由：开发者前端零基础，降低门槛
- 不选 React/Vue：学习成本 > ROI，阅读器的 UI 复杂度不需要框架
- 这个决定**可以被挑战**，如果未来 UI 复杂度显著上升（如插件市场）

## 未解决的技术问题（可以讨论）

1. **CSS Columns 分页的精确度**：CSS Columns 在跨浏览器/跨平台时可能有像素级偏差。是否需要自定义 JS 分页器？
2. **CFI 标注稳定性**：字号变化时 CFI 可能漂移。是否需要 text-content 哈希做 fallback 定位？
3. **大 EPUB（>100MB）的章节分割策略**：Rust 端是按 spine item 分割还是按实际内容大小动态分割？
4. **标注数据库的 schema**：一张表还是多表（标注/高亮/批注）？

## 提问约定

### 不要建议的事情
- 换成 React/Vue/Svelte（当前阶段不讨论）
- 加一个后端服务器（违反离线原则）
- 换到 Electron/Flutter（Tauri 已收敛）
- 用 epubjs 长期方案（已否决）
- 做用户系统/登录/云同步（当前不做）

### 可以大胆建议的事情
- Rust 端 HTML 清洗的具体算法
- CSS 分页器的实现细节
- 标注数据模型设计
- 导出格式（Markdown/JSON）
- Calibre 索引优化
- 跨平台兼容性处理
- 测试策略
- 性能优化方案
