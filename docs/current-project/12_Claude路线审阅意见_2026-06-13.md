> 日期：2026-06-13

## 一、总结论

- **认可「自有轻小说书库核心 + 来源连接器」路线。** Calibre / Kavita / Komga 任何一个当底座都会让数据模型迁就外部系统、让本项目退化成客户端。
- **最大风险不是合规，是 schema 演进时机。** `books` 单表与目标实体模型之间差一次伤筋动骨的迁移；协议 v0.5 要冻结 1.0，如果 `LibraryBook` DTO 以单表形状冻结，等于把单表模型焊死在协议里。
- **最应该马上做的：** 在 v0.5 冻结前完成 `LibraryBook` DTO 演进预留，并把 schema 迁移明确挂在 v0.5（已写入 `DECISIONS.md`）。

## 二、对审阅稿 10 个问题的回答

1. **自研书库核心 + 连接器 vs 依赖成熟系统**：自研核心正确。轻小说作品图谱（系列/卷/版本/语种/官方入口/本地资产/标注统一模型）目前没有竞品，是真实差异化。
2. **Calibre 只作迁移来源**：正确。不需要写回场景——标注导出走 Markdown/Obsidian，与 Calibre 无关；单向迁移避免写坏用户 metadata.db 的风险。
3. **Kavita / Komga 边界**：允许导入文件，不只是元数据。用户对自己服务器上的文件有访问权，下载+导入属 user_owned，合规。真正的边界：不缓存「浏览到但未导入」的正文、不把凭据用于权限之外的内容。建议这两个连接器用插件契约实现，作为官方样板插件（v0.6/v0.7）。
4. **OPDS 时机**：维持 v0.6，不提前。本地闭环和标注稳定之前不接在线目录。
5. **状态模型**：基本够用，但「资产状态」和「来源授权」混在一个枚举里。应拆成两个正交字段：`asset.availability`（local / remote / missing / cached）× `source_record.rights_status`（九个授权状态）。`metadata_only / external_link` 是「无 asset、只有 source_record」的自然结果，不需要专门状态。
6. **schema 迁移时机**：v0.5，与元数据模型同期。当前 `books.id` 即内容 SHA-256 前缀，annotations / reading_state 都以它为键——迁移只动书库层，**标注和进度键不动**。建议实体模型合并 work 层：`series → volume → edition → asset`，外传/短篇集用 `volume.kind` 区分，真需要 work 层再加。v0.5 前 reading-core 需补最简迁移框架（按 `PRAGMA user_version` 顺序执行迁移脚本）。
7. **插件契约能力**：采用「核心必选 + capability 可选」分层。必选 `search / getBook / getChapter`；可选 `browse / resolveUrl / fetchMetadata / acquire`，在 manifest 里声明。`acquire` 返回的授权状态由**宿主侧**执行能力限制矩阵，插件只是申报人。
8. **合规模型**：足够，层层都有（能力矩阵 + 授权九状态 + legal.kind 四级 + 域名白名单 + 宿主限速）。两个补强：矩阵必须在 Rust 宿主侧强制执行；`user-declared` 插件安装时加明示确认并在 UI 上与官方插件视觉区分。
9. **性能优先级**（按用户感知 × 当前风险）：① 书架封面（缩略图 + 懒加载）② 批量导入（并行流水线 + 进度 UI；桌面文件夹导入优先走路径版 `library.import` 而非 bytes 版）③ 持久化解析缓存（解析/分页结果落盘，二次开书读缓存）④ 搜索暂不用动 ⑤ 正文级全文索引推 v0.6+。
10. **Calibre 降级 UI**：符合方向。补充建议：首次启动检测到 Calibre 默认库存在时温和提示一次「检测到 Calibre 书库，要迁移吗」，主路径不绑定但不让 Calibre 用户自己翻菜单。

## 三、自研边界（后续讨论的结论，已写入 DECISIONS.md）

```text
自研（飞跃在此）：  书库模型、桥接协议、解析缓存管线的组织方式、插件契约
用现成（原材料）：  SQLite、FTS5/tantivy、QuickJS、reqwest、zip/quick-xml/sha2
不碰（无底洞）：    排版渲染引擎、UI 框架、数据库引擎、密码学、CRDT 算法
```

- 排版引擎维持「系统 WebView，不自写」不变。极致性能的路径是：协议留流式/批量语义 → v0.5 schema 实体化 → 持久化解析缓存 + 并行导入。
- WASM 唯一真实价值是远期「纯 Web 壳」的编译目标（reading-core 编译为 wasm32，实现 `ReaderBridge` 的 WASM 壳）。协议架构已天然支持，现在零动作；仅需注意 reading-core 不引入「只能原生」的重依赖时把它们隔离在 feature flag 后。
- 不换 TypeScript（ReScript / AssemblyScript / MoonBit 解决的是本项目没有的问题）。

## 五、建议优先级（确认审阅稿第 11 节，微调）

1. **v0.3.1**：实机冒烟（唯一发布阻塞）→ 打包测试版。
2. **v0.4**：标注增强 + 性能打磨（封面缩略图、并行导入、持久化解析缓存）。
3. **v0.5**：实体模型迁移（含迁移框架）+ 元数据模型 + `LibraryBook` DTO 终稿 + remote/metadata 条目书架 UI 规范 → 之后冻结协议 1.0。
4. **v0.6**：OPDS、Kavita、Komga、Calibre-Web 连接器（统一作品视图依赖 v0.5 实体模型先落地）。
5. **v0.7**：插件运行时 + 宿主侧能力矩阵强制。
6. **v1.0**：本地优先轻小说平台。
