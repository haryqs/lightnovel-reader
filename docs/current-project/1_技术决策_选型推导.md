# 技术决策：为什么选 Tauri + Rust 解析 + TS 分页

## 已评估的三种方案

### 方案一：Readium 全平台原生（Swift + Kotlin + TS）

| 维度 | 评价 |
|------|------|
| 渲染质量 | ★★★★★ 行业天花板，EPUB3 完全兼容 |
| 性能 | ★★★★★ 原生解析 + 原生导航器 |
| 开发成本 | ★☆☆☆☆ 需要 Swift + Kotlin + TS 三套代码，独立开发者不可行 |
| 移动端 | ★★★★★ 原生 iOS/Android |
| 离线 | ★★★★★ 全本地 |

**否决原因**：独立开发者没有双端原生人力，三套代码维护成本远超收益。

---

### 方案二：Tauri + epubjs / foliate-js（纯前端解析）

| 维度 | 评价 |
|------|------|
| 渲染质量 | ★★★☆☆ 依赖 JS 库质量，对格式差的旧 EPUB 无能为力 |
| 性能 | ★★★☆☆ JS 解压大 EPUB 阻塞主线程，移动端 OOM 风险 |
| 开发成本 | ★★★★☆ 一套 TS 代码通吃 |
| 旧 EPUB 兼容 | ★★☆☆☆ epubjs 不改 EPUB 样式；foliate-js 同样不洗 HTML |
| 长期维护 | ★★☆☆☆ epubjs 停滞（485 个 open issue）；foliate-js 个人维护不稳定 |

**否决原因**：
1. JS 库对 2010 年代格式差的旧 EPUB（乱码、恶性 CSS、`<font>` 布局、图片路径断裂）**没有清洗能力**
2. epubjs 已实质失维护，foliate-js 无 npm 发布且 API 不保证兼容
3. 对 30 年项目而言，依赖一个第三方 JS 库的风险不可接受

---

### 方案三：服务器后端解析 + 前端渲染（微信读书模式）

| 维度 | 评价 |
|------|------|
| 渲染质量 | ★★★★★ 服务端清洗 HTML |
| 性能 | ★★★★★ 毫秒级首屏 |
| 开发成本 | ★★☆☆☆ 需要运维服务器 |
| 离线 | ☆☆☆☆☆ **违反离线优先原则** |

**否决原因**：依赖服务器运维，违反"30 年不倒"的持久战约束。

---

## 最终选择：方案二升级版 —— Rust 解析 + TS 分页（Hybrid）

**不是纯粹用 JS 渲染引擎，而是把 EPUB 解析、HTML 清洗、编码转换等工作移到 Tauri 的 Rust 后端。前端只做分页和 UI。**

```
┌──────────────────────────────────────────────┐
│  前端 (TypeScript + Vite)                    │
│  ├─ CSS 分页器（原生 CSS Columns）            │
│  ├─ 标注叠加层（SVG overlay）                 │
│  └─ UI chrome（工具栏/目录/进度条）           │
├──────────────────────────────────────────────┤
│  后端 (Rust，Tauri commands)                 │
│  ├─ EPUB ZIP 解压 + OPF 解析                 │
│  ├─ HTML 清洗（去恶性 CSS、统一排版基线）      │
│  ├─ 编码检测/转换（GB2312 → UTF-8）          │
│  ├─ 图片路径修复 + 资源映射                   │
│  └─ Calibre SQLite DB 索引                   │
└──────────────────────────────────────────────┘
```

### 为什么这是最优解

1. **对旧 EPUB 无限修复能力**：Rust 端可以做任意深度的 HTML/CSS 清洗，不依赖任何 JS 库
2. **原生性能**：Rust 解压 ZIP、解析 XML，比 JS 版本快 5-10 倍，不阻塞 UI 线程
3. **内存安全**：按章加载，不把整本 epub 塞进 WebView；移动端抗 OOM
4. **不依赖第三方 JS EPUB 库**：30 年项目，核心解析逻辑必须在自己的 Rust 代码里
5. **Tauri v2 已支持移动端**：未来扩展到 iOS/Android 时，Rust 解析层无需重写
6. **离线优先**：全逻辑在客户端本地运行

### 与纯 foliate-js 方案的成本对比

| 维度 | Rust 解析 + TS 分页 | Tauri + foliate-js |
|------|---------------------|-------------------|
| MVP 工作量 | 2-4 周 | 1-2 周 |
| 旧 EPUB 清洗 | 完全可控 | 不可控 |
| 长期维护 | 自己的代码 | 依赖第三方 |
| 标注稳定性 | 自己控制 CFI 模型 | foliate-js 不稳定 API |
| 移动端扩展 | Tauri mobile 原生解析 | WebView 内 JS 解析 |

**结论：多花 1-2 周前期投入，换来 30 年不受制于人。这跟"持久战"的核心逻辑同构。**
