# 10. 独立桌面端 + 实时同步 + 极致性能 —— v1.0 架构方案

> 本文是方案文档 7（终局架构）和文档 8（桥接协议 v1.0-rc.1）之后的下一轮架构升级，
> 聚焦三件事：桌面端从“WebView 套壳”升级为真正独立软件、桌面端与网页端实时互通、
> 阅读体验性能打满。不推翻文档 7 的终局结论（reading-core + reader-engine + N 薄壳），
> 是在这个底座上加三块新能力。

## 0. 前提重申与一个需要先解决的张力

读完 `PROJECT_MEMORY.md` 的不可变约束后，有一条与本文目标 2 直接相关，必须先正面回应：

> **不可变约束：静态客户端优先，不做 SaaS。**

"网页端 ↔ 桌面端实时同步"天然需要一个服务端来中转/持久化变更。如果这个服务端被理解为
"本项目运营的云服务"，就违反了上述约束。本文的解决方案是：

- **同步服务器是用户自托管的组件，不是本项目运营的云服务。** 它是 reading-core 之外、
  与桌面壳同源代码仓库的一个独立小型 Rust 二进制（单文件、可 Docker 化），用户在自己的
  NAS/VPS/家庭服务器上跑一个，或者直接让"一台桌面端"内置同一份同步服务器逻辑充当
  局域网枢纽。项目方既不部署、也不运营、也不托管任何人的数据。
- 网页端因此不是"无后端依赖"的纯静态站点（这点会在目标 4 节里如实标注，不强行套用
  PWA 教条），但它依赖的后端是用户自己的，符合"本地优先 + 用户拥有数据"的精神，而不是
  传统 SaaS（项目方不运营、不计费、不托管）。
- 这与 AGPL 协议天然契合：自托管同步服务器本身也是 AGPL 代码，用户/社区可以审查、复用、
  二次部署。

后续所有"同步服务器选型"讨论都建立在"自托管"这个前提上，不再重复论证。

## 2. 更新后的总体架构图

```text
┌──────────────┬──────────────┬──────────────────────────────┐
│ 桌面壳(Tauri) │ 网页端(PWA)   │  （移动壳按文档7既有路线，不变） │
│ 托盘/文件关联 │ IndexedDB     │                               │
│ 自动更新      │ +OPFS         │                               │
├──────────────┴──────────────┴──────────────────────────────┤
│            reader-engine（同一份 TypeScript，渲染/UI/手势）   │
│   ┌─────────────────────────────────────────────────┐       │
│   │ Pagination Worker（新增）：WASM 分页 + 预渲染缓存  │       │
│   └─────────────────────────────────────────────────┘       │
├────────────────────── 桥接协议（扩展，非破坏） ─────────────────┤
│  reading-core(native, full)  │  reading-core-wasm(thin)      │
│  解析/清洗/书库/标注/插件宿主  │  解析/清洗/分页(无 SQLite)      │
│  + sync 模块（新增）          │  + sync 模块（同一份代码）      │
└────────────────────────────────────────────────────────────┘
                              │  WebSocket(实时) + REST(批量/blob)
                              ▼
                 ┌─────────────────────────────┐
                 │  自托管同步服务器（新二进制）   │
                 │  axum + SQLite，用户自己跑    │
                 └─────────────────────────────┘
```

关键决策：**reading-core 一分为二（features，不是两份代码）**——`full` feature（默认，桌面/移动用）带
SQLite 书库/标注/插件宿主；`wasm` feature（网页用）只编译纯计算部分（EPUB 解析、HTML 清洗、分页、
`compute_book_id`、sync 的冲突解决算法），不带任何 I/O。两者共享同一套 `lib.rs` 模块树，用
`#[cfg(feature = "...")]` 切，**不是 fork 一个新 crate**——避免"两份核心"的维护噩梦。

## 3. 目标一：真正独立的桌面端

### 3.1 决策表

| 子目标 | 方案 | 理由 / 权衡 |
|---|---|---|
| 系统托盘驻留 | **不需要 `tauri-plugin-tray`**（这个包不存在）。Tauri v2 的 `tray-icon` 是 `tauri` 主 crate 自带 feature，用 `tauri::tray::TrayIconBuilder` 直接建。 | 少一个外部依赖；官方一等公民支持，长期维护性更好。 |
| 窗口关闭→托盘 | 监听 `WindowEvent::CloseRequested`，调用 `api.prevent_close()` 改为 `window.hide()`；托盘菜单提供显式"退出"项才真正调用 `app.exit(0)`。 | 用户心智："关闭=最小化到托盘，退出要走菜单"是桌面应用通行约定（类比 Slack/Telegram）。 |
| .epub 文件关联 | `tauri.conf.json` 的 `bundle.fileAssociations` 声明 `.epub`；启动参数里的文件路径在 `tauri::Builder::setup` 里读 `std::env::args()`，配合 `tauri-plugin-single-instance` 把"双击第二个 epub"转发给已运行实例而不是开第二个进程。 | 不加 single-instance 会出现"每次双击 epub 都新开一个窗口"的体验灾难；这是文件关联的标准搭档插件。 |
| 自动更新 | 官方 `tauri-plugin-updater` + 签名密钥对；更新清单是一个**静态 JSON 文件**（`latest.json`），二进制可直接放 GitHub Releases。 | 静态清单 + 对象存储 = 不需要运营任何服务端，与"不做 SaaS"约束零冲突；这是 Tauri 生态的标准做法，不是自己发明协议。 |
| 原生右键菜单 | 分两层：①窗口/托盘菜单用 `tauri::menu::Menu`（原生）；②正文阅读区的右键菜单（复制/高亮/查词/添加书签）目前是浏览器默认菜单，升级为前端 `contextmenu` 事件拦截 + 新增桥接消息 `shell.showContextMenu(items, x, y): Promise<string | null>`，壳侧用 `tauri::menu::Menu::popup` 弹出真正的原生菜单。 | 正文区右键菜单本质是"业务功能入口"，不该让用户看到"复制/打印/检查元素"这种 WebView 默认项；用原生 popup 菜单比自绘 HTML 菜单更像独立软件。 |
| 冷启动 < 1s | 见 3.2 | — |

### 3.2 冷启动优化清单

读 `tauri.conf.json` 后确认：**生产构建已经是预构建静态资源**（`frontendDist: "../dist"`），
"去掉 Vite 预热"这个问题只存在于 `npm run tauri dev` 的开发态，**生产包不受影响**，不需要改建构流程本身。
真正影响冷启动的是以下几点：

1. **JS 包未做代码分割。** `src/main.ts` 一个文件里塞了阅读器、书库、OPDS、插件管理、批量关联面板的
   全部逻辑，首屏要解析执行全部代码。改造：用动态 `import()` 把"书库面板/OPDS 面板/插件面板/批量关联"
   四块拆成按需加载的 chunk，首屏只加载阅读器骨架 + 空状态。
2. **窗口先隐藏再显示。** `tauri.conf.json` 窗口配置加 `"visible": false`，前端 `DOMContentLoaded` 且首帧
   渲染完成后调用 `appWindow.show()`。避免"白屏窗口先弹出、内容再迟一拍出现"的视觉卡顿（这是 Tauri 应用
   最常见的体感卡顿来源，社区已验证）。
3. **SQLite 连接延迟初始化。** 当前 `library::init` 等是否在 `setup` 阶段就建连接需要确认；建议改为
   **首次访问书库命令时才开库**（lazy `OnceCell<Connection>`），冷启动路径不等数据库 I/O。
4. **生产构建关闭 devtools 自动打开**，确认 `tauri.conf.json` 没有遗留 `"devtools": true`。
5. **度量先于优化**：在 `setup` 钩子和前端 `onReady` 之间打时间戳日志，先建立"当前冷启动时间是多少"
   的基线，再逐项验证每条优化的实际收益——不要不测就堆优化。

## 4. 目标二：桌面端 ↔ 网页端实时同步（重点）

### 4.1 同步服务器选型

| 方案 | 优点 | 否决/采纳理由 |
|---|---|---|
| **自建 Rust 轻量服务器（采纳）** | 复用 reading-core 的 sync 冲突解决算法（同一份 Rust 代码，`wasm` feature 给前端，`native` 给服务端）；用户自托管，零运营成本，符合"不做 SaaS" | 唯一同时满足"不做 SaaS"与"reading-core 逻辑下沉"两条硬约束的方案 |
| 嵌入桌面端（"一台桌面端=同步枢纽"） | 不需要额外部署一个服务；适合"只有一台常开的桌面端 + 偶尔用网页端"场景 | **作为自建服务器的一种部署形态保留，而不是替代方案**：本质上是把同一个 sync 服务器二进制跑在桌面端进程内、监听局域网。文档把它写成"零配置模式"，但底层协议与独立部署版完全一致——这样用户从"零配置"升级到"VPS 常驻"不需要换协议。 |
| 依赖第三方（Supabase/Firebase/PocketBase 等） | 开发量最小 | 否决：把用户数据交给第三方云服务，直接违反"本地优先 + 用户拥有数据"的项目根基，也不符合 AGPL 的精神（核心逻辑变成不可审查的黑盒 SaaS） |

**结论**：服务端用 `axum`（异步、生态成熟、与 `reqwest`/`tokio` 共享依赖树，桌面壳已经在用 `reqwest`）
+ `rusqlite`（与 reading-core 同源技术栈，运维心智成本低，单文件部署）。新建 crate
`crates/sync-server`（独立二进制，依赖 `reading-core` 的 `sync` 模块做冲突解决，不重复实现）。

### 4.2 同步协议：WebSocket + REST 分工

| 通道 | 用途 | 理由 |
|---|---|---|
| WebSocket（`/sync/ws?library_id=&since=`） | 实时推送：新书加入、进度更新、标注增删、设备上线/下线心跳 | 低延迟、双向；"桌面端加一本书，网页端书架实时出现"必须靠 push，轮询做不到"实时" |
| REST 批量端点（`GET /sync/changes?since=cursor`） | 离线重连后的增量追赶；首次同步全量拉取 | WS 重连后丢的消息靠 REST 补，是离线优先系统的标准模式（参考 CouchDB/PouchDB 的 changes feed 设计），不重新发明 |
| REST 分块传输（`PUT /sync/blobs/{sha256}` + Range） | EPUB 文件本体同步 | 大字节绝不进 WS 消息体（与桥接协议"消息面只传引用"的纪律完全一致），用 HTTP Range 支持断点续传 |

### 4.3 数据模型：sync 字段设计

不新建一套平行表，**在既有迁移框架里追加新版本**，给需要同步的表加三个统一字段：

```sql
-- 追加到 edition / asset / annotations / reading_state 四张表（迁移新版本，ALTER TABLE ADD COLUMN）
last_modified  INTEGER NOT NULL DEFAULT 0,  -- epoch ms，每次写入由应用层置为 now()
sync_version   INTEGER NOT NULL DEFAULT 0,  -- 本设备上的单调递增版本号（不是全局版本，见 4.4）
deleted_at     INTEGER,                     -- NULL=未删除；软删除时间戳，墓碑而非物理删除
device_id      TEXT NOT NULL DEFAULT '',    -- 最后写入设备，冲突展示/调试用
```

并新增一张**变更日志表**（追加写、永不 UPDATE），作为同步的"事实来源"，而不是去 diff 整张表：

```sql
CREATE TABLE IF NOT EXISTS sync_outbox (
  cursor      INTEGER PRIMARY KEY AUTOINCREMENT, -- 本地单调游标，REST 拉取用这个分页
  entity_type TEXT NOT NULL,   -- 'edition' | 'asset' | 'annotation' | 'reading_state'
  entity_id   TEXT NOT NULL,
  op          TEXT NOT NULL,   -- 'upsert' | 'delete'
  payload     TEXT NOT NULL,   -- 整行 JSON 快照（与桥接协议 DTO 同形，复用 serde）
  device_id   TEXT NOT NULL,
  created_at  INTEGER NOT NULL
);
```

由 `edition`/`asset`/`annotations`/`reading_state` 的 `AFTER INSERT/UPDATE/DELETE` 触发器写入
`sync_outbox`——**复用项目已有的 FTS 触发器写法**（`books_fts`/`catalog_fts` 已经是这个模式），不是新模式。

为什么不直接同步整表：变更日志让"客户端断线 3 天后重连"只需要 `WHERE cursor > last_seen_cursor`，
代价是 O(变更量) 而不是 O(全库)；也天然给 WebSocket 推送提供逐条事件源。

### 4.4 冲突策略：按数据形态分层，不是一刀切 LWW

| 数据 | 冲突模型 | 规则 |
|---|---|---|
| 阅读进度（`reading_state`，每书一行，整行覆盖语义） | Last-Write-Wins | 比较 `last_modified`，新的整行覆盖旧的；`device_id` 仅用于"同一时刻并发"时的 tie-break（字典序）。阅读进度本质是"最后一次看到哪"，LWW 语义上就是对的，不需要更复杂的策略。 |
| 标注（`annotations`，每条标注是独立 UUID 行） | **行级 LWW + 字段级合并** | 不同标注 id 之间天然无冲突（不同行）；同一条标注被两端编辑（如都改了 `note`）才比较 `updated_at` 取新；**新增/删除不是同一行的更新，不存在"合并"问题**——这比通用 CRDT 简单得多，因为标注模型本身就是"集合的增删"而非"单值的并发编辑"。 |
| EPUB 文件 | **内容寻址去重，不存在冲突** | `bookId = SHA-256(epub)`；同一本书在两端必然算出同一个 hash，"同步"退化成"对方没有这个 hash 就传一份"，没有合并语义可言。 |
| 删除 vs 编辑的竞态 | **墓碑优先，但带时间窗** | 若 `deleted_at > last_modified`（删除发生在最后一次编辑之后）→ 删除生效；若编辑发生在删除之后（用户在 A 端删除标注的同时 B 端又编辑了它）→ 编辑"复活"该行并清空 `deleted_at`，因为更晚的用户意图是"这条还要"。这是标准的 tombstone-with-resurrection 规则，逻辑直白，前端也能解释给用户（"你的修改更新"）。 |

冲突解决算法实现在 `reading-core::sync` 模块（新增），纯函数、无 I/O，因此 `wasm` feature 下网页端
**用同一份算法在本地先做乐观合并**，不必每次都等服务器判定——这是离线优先体验的关键：网页端断网时
依然能立即看到自己的修改生效，重连后才与服务器对账，对账逻辑双端一致因为是同一份 Rust 代码编译两次。

### 4.5 身份认证：设备配对码（v1 不做账号系统）

流程：

1. 任意一端（通常是桌面端）首次开启同步时，生成 `library_id`（UUID）+ `pairing_secret`（32 字节随机），
   本地保存，同时显示为 6 位数字配对码 + 二维码（二维码内容是 `library_id + secret` 的紧凑编码）。
2. 第二端输入配对码或扫码，向同步服务器请求一个 **scoped bearer token**（按 `library_id` 限定，无法越权
   访问其他 library）。
3. 服务器只认 `library_id` 域，不认"用户"——这就是不做账号系统的具体含义：一个同步服务器实例可以挂多个
   独立的 library（多用户托管同一台服务器仍然数据隔离），但服务器本身不做注册/登录/密码管理。
4. token 仅存本地（桌面：OS keychain 优先，回退加密文件；网页：仅 `IndexedDB`，不落 `localStorage` 防 XSS
   读取），可在设置里"撤销并重新配对"。

这条路线把"账号系统"完全推到"v1 不做"的范围之外，但保留了"以后要做账号系统"时的扩展点：
`library_id` 可以未来挂到一个真正的账号下，协议不需要改。

### 4.6 首次同步策略

- **全量**：新配对设备首次连接，直接 `GET /sync/snapshot`（服务器侧聚合当前全部存活行，按表分页返回），
  这比"从 cursor=0 重放全部 outbox"快得多（outbox 会包含大量已经被覆盖的历史中间态）。
- **增量**：之后所有同步走 `sync_outbox` 的 cursor 增量。
- **EPUB blob**：snapshot 阶段只下发"应该有哪些 hash"的清单，**不在快照里夹带文件内容**；客户端对照本地
  对象仓库缺哪些 hash，再按需逐个 `GET /sync/blobs/{sha256}`——与桥接协议"大字节走资源通道"的纪律一致，
  同步协议照搬这条纪律而不是另起一套。

### 4.7 桥接协议的扩展（不破坏冻结面）

新增方法都遵守文档 8 的规则 2"新增能力=新增方法"，**不改动任何已冻结的 `1.0-rc.1` 方法签名**：

```ts
// sync.pair — 用配对码/二维码内容换取 token，写入本地凭据
syncPair(code: string): Promise<SyncCredential>
// sync.status — 当前同步状态（已配对/未配对、最后同步时间、待上传变更数）
syncStatus(): Promise<SyncStatus>
// sync.now — 手动触发一次同步（debug/用户主动点"立即同步"）
syncNow(): Promise<void>
// sync.unpair — 撤销配对
syncUnpair(): Promise<void>
// event: sync.changed — 服务器推送的变更事件（书架/进度/标注），引擎订阅后刷新对应 UI
```

## 5. 目标三：极致性能

### 5.1 reading-core 加 WASM target：依赖改造

| 依赖 | 现状 | WASM 下的处理 |
|---|---|---|
| `rusqlite(bundled)` | 静态链接 C SQLite | `wasm` feature 下整个不编译进去；`library`/`storage`/`plugin_store` 等模块用 `#[cfg(feature = "native")]` 包起来 |
| `zip` | 纯 Rust，可编译 wasm | 保留，EPUB 本质是 zip |
| `quick-xml` | 纯 Rust | 保留 |
| `encoding_rs` | 纯 Rust（Mozilla 出品，本就为 wasm 场景设计） | 保留 |
| `sha2` | 纯 Rust | 保留 |
| `image`（png/jpeg） | 纯 Rust 解码 | 保留，但评估是否值得为减体积换成仅在原生端启用——网页端缩略图可以交给浏览器 `<canvas>` 生成，不必占 wasm 包体积；建议网页端这块用 `#[cfg(feature = "native")]` 关掉，改用 JS 侧生成缩略图 |
| `csv` | 纯 Rust | 青空文库连接器整体是"壳层 HTTP + core 解析"，网页端没有这条连接器需求（v1 范围内网页端不做这些来源连接器），整个 `connectors` 模块网页端可以不编译 |
| 新增 `tl`（HTML 解析） | 无 | 为分页迁移新增；选 `tl` 而非 `html5ever`/`scraper`：`tl` 是 zero-copy、专门为速度和小体积设计、被广泛用在 wasm 场景，`html5ever` 体积大很多且 API 更重 |

`Cargo.toml` 改造方向：

```toml
[features]
default = ["native"]
native = ["rusqlite", "image", "csv"]   # 桌面/移动用，全量
wasm = []                                # 网页用，纯计算

[dependencies]
rusqlite = { version = "0.32", optional = true, features = ["bundled"] }
image = { version = "0.25", optional = true, default-features = false, features = ["png", "jpeg"] }
csv = { version = "1", optional = true }
tl = "0.7"
```

### 5.2 分页计算迁移：`buildVirtualPages()` → Rust

新增 `crates/reading-core/src/pagination.rs`（无 feature 限制，两端都编译），把
`reader-core.ts` 里的 `buildVirtualPages` / `elementToPageBlocks` / `splitText` / `estimateBlockCost`
四个函数原样移植为 Rust：

- 用 `tl` 解析章节 HTML 得到元素树，替代 `DOMParser`（Worker 里没有 `DOMParser`，这是迁移的硬约束）。
- 容量估算公式（`getEstimatedPageCapacity`）保持现有启发式（基于视口宽高/字号的字符数估算），
  **不是真实文本测量**——这点现状如此，迁移不引入新的"真实测量"诉求，因为真实测量需要 `canvas.measureText`，
  这只有主线程/Worker 里的 `OffscreenCanvas` 能做。本次迁移目标是"把现有算法挪出主线程"，不是"做新算法"；
  真实测量留作后续可选优化（见 5.3 末尾的"已知局限"）。
- 输入输出签名：

```rust
pub fn paginate(html: &str, capacity: usize) -> Vec<String> // 返回每页 HTML 字符串数组
```

- 经 `wasm-bindgen` 导出为 `paginate_pages(html: String, capacity: usize) -> Vec<String>`。

### 5.3 Web Worker 架构

```text
主线程                          Pagination Worker
  │  postMessage(chapterHtml, capacity, key)
  ├──────────────────────────────▶│  wasm.paginate_pages(...)
  │◀──────────────────────────────┤  postMessage(pages, key)
  │ pageModelCache.set(key, pages) │
```

- 主线程职责收窄为：渲染当前页 `innerHTML`、监听输入手势、维护 `pageModelCache`（沿用现有 LRU 缓存逻辑，
  缓存键不变）。
- Worker 启动时一次性 `instantiate` wasm 模块（常驻，不是每次分页都重新加载）。
- `getChapterHtml` 仍在主线程做（走 `bridge.getChapter`），只把"分页计算"挪到 Worker——保持现有
  预加载/缓存机制（`chapterCache`/`preloadAroundChapter`）不变，只替换 `getOrBuildPageModel` 内部
  从"同步调用 `buildVirtualPages`"改为"向 Worker 发消息 + Promise 等待"。
- **已知局限（如实记录，不过度承诺）**：Worker 方案解决的是"大章节分页计算阻塞主线程"，不解决
  "字符计数式容量估算在极端字体/CJK 标点密度下的轻微误差"——这个误差现状就存在，本次不在范围内修。

### 5.4 缓存策略

- 分页结果缓存：沿用 `pageModelCache`（LRU，现有 `maxPageModels = 8`），键不变（href+pageMode+fontSize+
  viewport+layout）。
- 章节预渲染：沿用 `preloadAroundChapter`（前一章/后一章/后两章），现状已经做了，不需要新增；
  唯一变化是预加载到的章节 HTML 现在还会顺带丢给 Worker 提前分页（"预分页"），翻页瞬间命中缓存。

### 5.5 GPU 翻页动画

当前 `renderCurrentPages()` 是整段 `innerHTML` 替换，**零动画**。改造为双层叠放 + transform 滑动：

```css
.reader-page-window { position: relative; overflow: hidden; }
.reader-page-layer {
  position: absolute; inset: 0;
  will-change: transform;
  transform: translate3d(0, 0, 0);
  transition: transform 220ms cubic-bezier(.2,.7,.3,1);
}
```

翻页时：新内容渲染到"下一层"（`translateX(100%)` 起始位），同一帧内用 `requestAnimationFrame` 触发
两层同时 transform 到位（当前层出、下一层入），动画结束后把"下一层"提升为当前层、移除旧层——
这是标准的双缓冲滑动翻页实现，全程只动 `transform`，触发合成器加速，不触发重排重绘。

### 5.6 性能目标验收口径

| 指标 | 目标 | 验收方式 |
|---|---|---|
| 冷启动 | < 1s | 从进程启动到首屏可交互的时间戳日志，Release 构建测 |
| 大章（>10000字）分页 | < 50ms | Worker 内对 wasm `paginate_pages` 调用计时，取 P95 |
| 书库搜索 | < 100ms | 已用 trigram FTS5，现状预期已达标；本次只需补一条基准测试脚本验证，不需要改实现 |
| 翻页动画 | 60fps | Chrome DevTools Performance 面板录制，确认无主线程长任务 |

## 6. 网页端落地

### 6.1 reading-core WASM → npm 包

`wasm-bindgen` + `wasm-pack build --target web --features wasm`（关闭 `default-features`，只启用
5.1 节的 `wasm` feature），产出发布为 `@lightnovel-reader/core-wasm`（私有/内部 npm 包，不依赖外部仓库）。

### 6.2 网页端存储：IndexedDB + OPFS

| 数据 | 存储 | 理由 |
|---|---|---|
| 书库元数据（系列/卷/版本） | IndexedDB | 结构化查询需求不重，IndexedDB 的 key-range 查询够用；与同步层的 `sync_outbox` 概念对应一份 JS 实现（不是 Rust，因为网页端没有 SQLite，变更日志直接用 IndexedDB 的一张 object store 模拟） |
| 标注/阅读进度 | IndexedDB | 同上，量级小 |
| EPUB 文件本体 | **OPFS（Origin Private File System）** | 体积可能到几十 MB，IndexedDB 存大 blob 性能差且部分浏览器有限制；OPFS 是为这种场景设计的（Chrome/Edge 已支持，Safari 16.4+ 支持），且支持流式读写，适合"分块同步"落盘 |
| 搜索 | IndexedDB 游标 + 内存里跑一次简单的子串匹配（网页端书库量级远小于本地全量书库，不需要 FTS5 trigram 那套） | 避免在网页端重新实现一套 FTS；网页端书架预期是"常用的几十到几百本"，线性扫描足够快 |

### 6.3 网页端部署

静态站点（Vite build 产物），**唯一的非静态依赖是用户自己的同步服务器地址**（在设置页填写，不是项目方
托管的固定域名）。这与第 0 节的立场一致：项目方不运营任何后端，网页端能不能同步完全取决于用户是否配置
了自己的同步服务器；不配置时网页端退化为"纯本地阅读器"，功能仍然完整（开 epub、读、标注、进度，只是
不跨端）。

### 6.4 PWA

`vite-plugin-pwa` 接入：离线可用（Service Worker 缓存静态资源 + 已下载的 EPUB 走 OPFS 不受影响）、
"添加到主屏幕"。PWA 是锦上添花项，不阻塞 Phase 1/2，排在 Phase 4。

## 8. 不做什么（边界重申）

- **不做 Electron 迁移**：违反体积约束（文档 7 已否决，本文档不重开）。
- **不自写排版引擎**：ruby/竖排/禁则处理硬约束不变，分页"计算"迁移到 Rust 不等于"渲染"迁移——
  实际排版渲染依然 100% 交给系统 WebView 的 CSS 引擎，Rust 只做"在哪里切页"的计算，不碰任何排版/
  字形渲染逻辑。
- **不做账号系统 v1**：见 4.5，用设备配对码；账号系统是否要做、何时做，留给以后单独评估，本文不预支
  这个决定。
- **不运营同步云服务**：见第 0 节，自托管是贯穿全文的硬前提，不是"先做 SaaS 版本以后再开源"的过渡状态。
- **不为网页端重做 FTS5 trigram 搜索**：网页端书架量级不需要，过度设计。
- **不在本次引入插件运行时的 QuickJS/JavaScriptCore 执行**：那是文档 7 的 v0.7+ 路线，与本文三个目标
  正交，不在本文范围内推进或拖慢。

## 9. 风险登记

| 风险 | 缓解 |
|---|---|
| `reading-core` feature 拆分引入编译矩阵复杂度（native/wasm 两套 CI） | 复用既有 `check:project`/`cargo test --workspace` 习惯，新增 `cargo build --no-default-features --features wasm --target wasm32-unknown-unknown` 作为第二条 CI 检查；两套构建任何一边失败都算红 |
| `tl` 的 HTML 解析行为与浏览器 `DOMParser` 在边缘情况（畸形 HTML、自闭合标签宽容度）不完全一致 | EPUB 章节 HTML 来自 `html_sanitizer` 清洗后的产物，已经是受控的干净 HTML 子集，不是任意网页；迁移后用现有书籍跑分页快照对比测试（旧 TS 实现 vs 新 Rust 实现逐页输出 diff），不一致再针对性修 `tl` 调用方式 |
| 同步冲突解决规则（4.4）在真实多设备并发场景下出现未预见的边缘情况 | 先用"行级 LWW + 墓碑复活"这套最简规则上线，配合 `sync_outbox` 全量留痕（出问题可回溯每一条变更的真实顺序），不要在第一版引入向量时钟/CRDT 这类更复杂但当前数据模型不需要的机制 |
| 自托管同步服务器的运维门槛劝退非技术用户 | 桌面端内置"零配置模式"（4.1 节），把同一份服务器逻辑跑在本机回环地址，最低门槛是"两台设备在同一局域网，桌面端常开"；VPS/NAS 部署是进阶选项，不是唯一路径 |
| OPFS 浏览器兼容性（Safari 较新才支持） | 网页端在不支持 OPFS 的浏览器降级为"仅元数据/标注同步，EPUB 本体仍需本地导入"，功能降级而非整体不可用，并在 UI 上明确提示 |
| Web Worker + wasm 的调试体感比同步调用差（栈追踪、热重载） | Phase 1 阶段保留一个 TS 实现的 fallback 路径（`buildVirtualPages` 原函数暂不删除，加 feature flag 切换），等 Worker 方案稳定跑过一个迭代周期再清理旧代码 |
