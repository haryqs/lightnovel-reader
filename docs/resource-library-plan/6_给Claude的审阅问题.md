# 给 Claude 的审阅问题

> 这份文档用于交给其他 AI 或开发者审阅。请重点批判方案的盲点，而不是重复赞同。

## 需要重点审阅的问题

1. **产品定位是否成立**
   - “本地优先阅读器 + 全球书目图谱 + 合法入口”是否比“资源聚合 App”更可持续？
   - 这个定位对轻小说用户是否有足够吸引力？

2. **不使用 Calibre 作为底座是否正确**
   - 自建 SQLite 书库是否会重复造轮子？
   - 是否应该兼容 Calibre，而不是替代 Calibre？
   - 有没有更好的本地书库格式？

3. **数据模型是否过度设计**
   - `series / work / volume / edition / asset / source` 是否必要？
   - 对轻小说而言，是否还需要 `chapter`、`translation_group`、`publisher_imprint`、`related_media`？
   - 是否应该一开始简化，只保留 `book / file / source`？

4. **在线资源接入是否过于保守**
   - 只做元数据、官方入口、OPDS，会不会不满足用户对“资源”的期待？
   - 有没有合法但资源量更大的接入方式？
   - 是否可以设计“用户本地私有规则”，同时让官方项目不背责？

5. **版权边界是否足够清晰**
   - 授权状态矩阵是否合理？
   - `official_free` 是否应该允许缓存？
   - 用户自定义源、社区源、插件市场之间的责任边界如何划分？

6. **MVP 顺序是否正确**
   - 是否应该先做本地 EPUB 阅读，再做书库？
   - 是否需要一开始就做 SQLite？
   - 在线能力应在第几个版本加入？

7. **跨平台策略是否现实**
   - Tauri v2 覆盖 Win/Linux/mac/iOS/Android，但实际移动端文件权限和 WebView 差异是否会拖垮项目？
   - 是否应先只承诺桌面端？
   - 鸿蒙是否应作为远期目标，而不是早期目标？

8. **开源生态策略**
   - AGPL 是否适合这类阅读器？
   - 插件是否也必须 AGPL 兼容？
   - 如何避免插件生态变成侵权源生态？

## 希望 Claude 输出的内容

请从以下角度给建议：

```text
1. 最严重的产品风险
2. 最严重的技术风险
3. 最严重的版权/合规风险
4. 数据模型删减建议
5. MVP 重新排序建议
6. 是否存在更好的合法资源最大化方案
7. 是否建议把该方案并入当前阅读器项目
```

## 当前方案的自我怀疑

1. 方案可能过于理想化，轻小说用户可能更关心“能不能直接读到内容”。
2. 合法入口聚合的资源量很大，但转化为可读正文的比例可能低。
3. 书目图谱维护成本高，尤其是跨语种、译名、卷序、版本合并。
4. 插件机制很容易被用户拿去做高风险源。
5. 移动端体验可能比桌面端复杂得多。

## 当前暂定立场

即使有上述疑虑，仍建议坚持：

```text
不内置盗版源
不分发侵权正文
不绕过付费/登录/DRM
本地阅读体验优先
资源最大化靠书目和入口聚合
```

这条路线不一定最快吸引用户，但更适合作为长期、开源、可持续的数字公共品。
