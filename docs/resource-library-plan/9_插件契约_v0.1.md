## 一、为什么契约先行

1. iOS 的 App Store 2.5.2(下载代码只许 WebKit/JavaScriptCore 执行)决定了插件必须
   写在"引擎无关的纯 JS 子集"上。这个约束必须从第一份插件就生效,否则 v0.9 iOS
   版要推倒社区已有的插件。
2. "过滤尽可能准确"的实现位置在插件(站点专属 CSS 选择器),不在核心算法。契约
   越早稳定,积累的站点规则越早开始。

## 二、运行时形态(v0.7 实现)

- 桌面 / Android / 鸿蒙:QuickJS(经 `rquickjs` 嵌入 reading-core 的 `plugin-host` 模块)。
- iOS:系统 JavaScriptCore,同一套 host API 桥到 Rust。
- 插件代码两个引擎一字不改;`host` 对象的所有真实能力(HTTP、HTML 解析、KV)在
  Rust 侧实现,JS 引擎只是调度器。
- 宿主注入的标准全局仅 `URL`、`TextDecoder`,两引擎行为由宿主拉齐。

## 三、安全模型

| 层 | 机制 |
|---|---|
| 能力白名单 | 插件只能调 `host.http/html/kv/log`;不存在 fs、进程、eval、动态 import |
| 网络域名白名单 | `manifest.domains` 精确匹配,越界请求 Rust 侧直接拒绝 |
| 存储隔离 | `host.kv` 按插件 id 分桶,互不可见,也碰不到书库数据库 |
| 请求头控制 | User-Agent/Referer 由宿主统一设置,插件不可伪装 |
| 安装时知情 | manifest 的 domains/permissions/legal 逐项展示给用户确认 |
| 每域限速 | 桌面壳在 app 范围按精确域名共享调度，同域 HTTP 请求最短间隔 1 秒 |

## 四、合规边界(承接文档 4)

- `legal.kind` 四级:`public-domain` / `open-license` / `official-free` / `user-declared`。
- 官方仓库只收前三级;`official-free` 必须遵守源站 ToS(含抓取频率限制,宿主侧
  v0.7 实现统一的每域限速)。`official-free + HTTP` 必须声明 HTTPS `legal.termsUrl`，安装前展示并要求用户确认。
- 内核零内置源;`user-declared` 的插件只能用户自装,官方不索引、不推荐、不分发。
- `user-declared` 插件安装时必须有明示确认(“此源的合法性由你自行负责”),且 UI 上
  与官方插件视觉区分——让“官方不背书”从条款变成产品事实。(2026-06-13)

## 五、插件作者体验(设计目标)

写一个源 = 一个目录两个文件,三个函数:

```text
my-source/
├── manifest.json    # 声明
└── plugin.js        # export default { search, getBook, getChapter, ...可选 capability }
```

插件分发格式先采用目录 zip。宿主侧读取规则：

- zip 根目录可直接放 `manifest.json` / `plugin.js`,也可包一层目录。
- 包内只能有一个 `manifest.json`。
- `manifest.entry` 只能是单个 `.js` 文件名,不允许目录、绝对路径或 `..`。
- 入口脚本必须与 `manifest.json` 在同一目录。
- 安装前只读取 manifest 与入口文本并做策略校验,不执行插件代码。
- 桌面壳用原生文件选择器取得 zip 路径，再由壳侧读取文件交给 core；协议不传插件 zip 字节。

安装确认规则：

- 安装前 UI 必须展示 `domains`、`permissions`、`capabilities`、`legal.kind` 与 core 返回的 warnings。
- `legal.kind=user-declared` 必须要求用户显式勾选确认，未确认时 core 拒绝写入插件目录。
- `legal.kind=official-free` 且申请 `http` 时必须声明 `legal.termsUrl`；安装预览提供打开条款入口，未确认时 core 同样拒绝写入。
- 已安装且 `enabled=true` 的插件可由桌面 QuickJS 运行时执行；未安装或停用插件不得进入运行时。
- 已安装插件带 `enabled` 状态，停用插件仍保留文件与元数据，但后续运行时不得加载。
- 重新安装同 id 插件时，宿主先删除旧插件目录再写入新包，避免旧入口文件或辅助文件残留。
- 卸载插件只删除 app data 下对应插件目录，不删除书库、远程条目或用户阅读数据。
- 运行时执行前必须先经过 `reading-core::plugin_host::ensure_method_allowed`：
  `search/getBook/getChapter` 是必选方法，`browse/resolveUrl/fetchMetadata/acquire` 必须与
  `manifest.capabilities` 对应；`enabled=false` 的插件不得运行任何方法。
- `host.http` 每次调用都重新校验域名/请求头/超时；壳层不跟随重定向、拒绝本机与内网目标，
  响应体上限 8 MiB；所有 Runtime 共用 app-wide 每域调度器，同域请求最短间隔 1 秒。`host.html` 输入和返回 JSON上限 8 MiB，单条日志上限 4 KiB。
- SDK 返回的书籍、章节与封面 URL 同样必须落在 `manifest.domains` 精确白名单内；
  `search` 单页最多 200 条，`getBook` 最多 20,000 章，URL/标题/简介另有长度上限。
- 每次方法调用使用一次性 Runtime/Context，QuickJS 堆上限 64 MiB，CPU/HTTP 时限共享 25 秒截止时间。

**必选三函数**:

- `search(query, page)` → 搜索结果列表
- `getBook(bookUrl)` → 书籍详情 + 章节列表
- `getChapter(chapterUrl)` → 单章 HTML(只许文本类标签,入库前还会过 core 清洗)

**正式来源流程**：

- `source.list` 只列已启用插件；安装、启停、卸载继续归 `plugin.*` 管理面。
- `source.search` / `source.getBook` / `source.getChapter` 分别执行三个必选函数，不复用诊断用 `plugin.testFlow`。
- `source.search` 只返回候选，不写书库。用户点击“收藏来源”后，`source.collect` 会重新执行 `getBook`，
  用插件 id + 规范书籍 URL 派生稳定去重键，写入 `source(kind=plugin)` 与远程 `source_record`。
- 收藏只保存元数据和源站外链。`public-domain/open-license` 的可获取策略仍需走独立 acquire 门；
  `official-free` 与 `user-declared` 不会因收藏而自动下载、缓存正文。

**可选 capability**(2026-06-13 确立,与文档 3 的 Source Adapter 接口统一;
manifest 中以 `capabilities` 数组声明,宿主据此展示与路由):

- `browse(path, page)` → 无搜索词的分类/排行/目录浏览(多数源站有,OPDS 必备)
- `resolveUrl(url)` → 识别用户粘贴的 URL,返回书目/来源记录(官方链接识别器入口)
- `fetchMetadata(remoteId)` → 仅元数据源使用,返回书目信息,不涉及正文
- `acquire(remoteId, mode)` → 申报获取方式与授权状态;**能力限制矩阵(文档 3)由
  宿主在 Rust 侧强制执行**,插件返回值只是申报,宿主依据授权状态决定是否放行
  下载/缓存,不信任插件自报

v0.7 第一版宿主策略：`metadataOnly` 可用于外链/元数据流程；`download` / `cacheForReading`
只允许 `public_domain` 与 `open_license`。`official_free` 继续只做 metadata + 官方入口，
即使通用 ToS/限速门已落地，也必须另做单源授权审核后才可能放行。`unknown` 与 `user-declared`
不得被官方运行时自动下载/缓存正文。

正式获取由新增的 `source.acquire(pluginId, bookUrl)` 承载：运行时重新执行 `getBook` 与
`acquire(bookUrl, 'cacheForReading')`，宿主只接受 `mimeType=application/epub+zip`，并在下载后验证
EPUB 结构再挂到已收藏/同步收藏的远程 edition。下载字节不经过前端消息面，直接进入本地对象仓库。

代码层约束：`manifest.schema.json` 与 `reading-core::plugin_manifest` 都必须认识同一组 capability：
`browse`、`resolveUrl`、`fetchMetadata`、`acquire`。新增 capability 时必须同步 SDK schema、
`source-plugin.d.ts`、Rust enum、本文档与开发记忆。

类型提示由 `host-api.d.ts` + `source-plugin.d.ts` 提供,作者在任何编辑器里有补全。

## 六、官方仓库索引(v0.7 骨架)

官方仓库索引用于发布“可被官方 UI 展示的白名单插件候选”，不是通用插件市场，也不是自动安装列表。
代码层权威文件为 `plugin-sdk/repository.schema.json` 与 `reading-core::plugin_repository`。

索引条目包含：

- `manifest`：完整插件 manifest，仍需通过 `plugin_manifest` 校验。
- `packageUrl`：插件 zip 包 HTTPS 下载地址。
- `packageSha256`：zip 包 SHA-256 hex；下载后必须逐字节核对。
- `packageSize`：可选包大小提示，当前上限 50 MiB。
- `sourceUrl`：可选源码/审阅页面，必须 HTTPS。
- `signature`：zip 原始字节的 `ed25519` 签名；`value` 为标准 Base64，`keyId` 指向客户端编译内可信公钥。

官方索引额外规则：

- 拒绝 `user-declared` 插件；这类插件只能用户自装，官方不索引、不推荐、不背书。
- 拒绝重复插件 id。
- 拒绝非 HTTPS 包地址/源码地址。
- `official-free + acquire` 需要单源正文授权审核，当前不得进入官方索引。

安装链路是：索引元数据/keyId 校验 → 壳下载 zip → 校验 `packageSha256` → 如声明签名则对 zip 原始字节
做 Ed25519 验签 → `plugin_package` 读取 zip → `plugin_store` 安装前确认/写入。预览与安装各自重新下载和验签，
不信任前一次结果。正式发布公钥尚未配置前，unsigned 条目只在明确的人工白名单模式下放行并显示 warning；
任何未知 keyId、无效 Base64 或坏签名都拒绝。索引通过不代表插件已安装或可执行。

## 七、版本规则

- `manifest.apiVersion` 对应 host API 版本,当前 `0.1`(自由修改期)。
- 运行时落地(v0.7)时升 `1.0` 并冻结:此后只增不改;破坏性变更升大版本,宿主
  按 apiVersion 路由到兼容实现。
