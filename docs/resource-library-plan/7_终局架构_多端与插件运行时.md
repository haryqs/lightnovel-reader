# 终局架构:多端与插件运行时

> 前提更新:① Android / iOS 是硬性目标,不是远期可选;② 开发模式为 AI 协作,样板代码的产出成本大幅下降,"需要写很多壳"不再是否决理由。
> 本文在 `5_技术路线与MVP.md` 基础上做架构修订:不推翻 v0.2–v0.6 路线,而是把它放进多端终局框架里,并补上插件运行时设计。

## 一、结论

**一份 Rust 核心(reading-core)+ 一份 TypeScript 阅读引擎(reader-engine)+ N 个薄平台壳(系统 WebView)。**

- 不换 Flutter,不嵌 Servo,不做纯 Rust GUI。
- Tauri 保留,但降级定位为"第一代桌面/移动壳"。通过桥接协议隔离后,任何一端的壳都可独立重写、互不牵连。
- 真正需要自构的只有三件:**桥接协议**(让壳变薄的关键)、**插件运行时**(Tauri 没有的、产品的核心差异点)、**reading-core 的边界纪律**(逻辑全部下沉)。

## 二、三条不可违抗的硬约束(推导起点)

架构不是偏好问题,是约束求交集:

1. **轻小说排版 = ruby(振假名)+ 竖排 + 禁则处理 + 傍点。** 这些只有 CSS 引擎原生支持(`<ruby>`、`writing-mode: vertical-rl`、`line-break: strict`、`text-emphasis`)。自写排版 = 重做 HarfBuzz + ICU + 盒模型,数百人年量级——这不是"打字量"问题,AI 辅助也不改变其不可行性。
2. **iOS / Android 硬性要求。** iOS 上系统免费提供且过审无虞的渲染/脚本引擎只有 WKWebView / JavaScriptCore;自带引擎(Servo 等)在移动端不成熟且吃体积。
3. **体积极小。** 唯一路径是不打包渲染引擎、复用系统 WebView。Flutter(20–40MB)和 Electron(80MB+)都直接违反。

三条约束的交集只有一个:**系统 WebView 做渲染层,所有逻辑下沉 Rust,所有 UI 收敛为一份 TS。**

## 三、被否决的备选(记录否决理由,防止将来反复)

| 方案 | 真实优势 | 否决理由 |
|---|---|---|
| Flutter | 渲染全端一致;有 OpenHarmony 分支 | **竖排 CJK 文本至今无原生支持,ruby 需自造**(对轻小说是致命伤);全量重写;Dart;体积 20–40MB |
| Servo 嵌入 | 全端渲染一致的理想方案;Rust 原生 | 移动端不成熟;鸿蒙无支持;体积大。**3 年后作为桌面可选引擎重评** |
| 纯 Rust GUI(egui/Iced/Slint) | 极小极快 | CJK 小说级排版能力不足,见约束 1 |
| Electron / CEF | 生态最熟 | 体积与内存,直接违反初衷 |
| Compose Multiplatform | 移动端强 | 排版同样要自己解决;桌面端不复用现有 TS 资产 |

## 四、终局架构

```text
┌─────────────┬─────────────┬─────────────┬─────────────┐
│ 桌面壳 ×3    │ Android 壳  │ iOS 壳       │ 鸿蒙壳(远期) │   薄壳:只做"WebView+消息管道+平台权限"
│ Tauri v2    │ Kotlin      │ Swift       │ ArkTS       │
│ (wry)       │ +WebView    │ +WKWebView  │ +ArkWeb     │
├─────────────┴─────────────┴─────────────┴─────────────┤
│        reader-engine(同一份 TypeScript)               │   分页/竖排/ruby/主题/手势/标注 UI
├────────────────── 桥接协议(JSON 消息)──────────────────┤
│        reading-core(同一份 Rust)                      │   解析/清洗/书库/标注/插件运行时
└────────────────────────────────────────────────────────┘
```

### 4.1 reading-core(Rust,编译到所有端)

- 模块:`epub`(解析+HTML 清洗)/ `library`(SQLite+FTS5)/ `annotation` / `plugin-host` / 将来 `sync`。
- 目标平台:win/mac/linux(x64+arm64)、`aarch64-apple-ios`、`aarch64-linux-android`、`aarch64-unknown-linux-ohos`(Rust 官方 tier-2 鸿蒙目标,已存在)。
- HTTP:`reqwest` + `rustls`(避开 OpenSSL 在移动端交叉编译的地狱)。
- 绑定方式:桌面走 Tauri command;Android/iOS 用 UniFFI 生成 Kotlin/Swift 绑定;鸿蒙走 C ABI + NAPI。
- **FTS5 中日文检索注意**:默认 `unicode61` tokenizer 对 CJK 基本不可用(连续汉字会被并成一个 token)。起步即用内置 `trigram` tokenizer(SQLite ≥3.34,支持 CJK 子串检索),后续有需要再换分词型自定义 tokenizer。

### 4.2 reader-engine(TypeScript,一份代码全端跑)

- 即现有 `reader/src/` 的延续:虚拟页分页、双页、主题、手势、标注 UI。已有投入全部保留。
- **架构纪律(v0.2 起立即执行)**:
  1. 前端禁止直接 `import @tauri-apps/api`,一律经 `platform` 适配层(抽象出 `invoke()` / `listen()` / `openFile()` 等接口)。这是壳可替换的前提,现在不做,将来移动端要付十倍代价拆。
  2. 新业务逻辑写进 core crate,不写进 Tauri command 的胶水函数里。
- CSS 特性预算(只用这些,保证全端 WebView 一致):`column-*`、`writing-mode: vertical-rl`、`text-orientation`、`<ruby>`、`text-emphasis`、`line-break: strict`。全部是 WebView2 / WKWebView / Android WebView / ArkWeb 的现代版本已支持的特性。

### 4.3 薄壳 ×4

每个壳的职责被桥接协议压缩到:创建 WebView、把消息通道接到 core 入口、申请平台权限(文件/网络)、打包签名。量级是几百到一两千行——这正是 AI 协作最擅长批量生产的部分,也是"多端"从不可行变为可行的底气。

- 桌面:Tauri v2(现状保留,零迁移成本)。
- Android:先试 Tauri v2 mobile;若成熟度出问题,fallback 为手写 Kotlin 壳(WebView + UniFFI)。**因为有桥接协议,fallback 的成本 = 重写一个壳,而不是重写 App。**
- iOS:同上,WKWebView + `WKScriptMessageHandler`。
- 鸿蒙:ArkTS + ArkWeb + NAPI 调 core,明确标记为远期。

### 4.4 桥接协议(让壳变薄的关键自构件)

- 一套 JSON 消息协议定义 engine ↔ core 的全部通信:request / response / event(如 `book.open`、`page.content`、`annotation.create`、`source.search`)。
- 协议在 v0.5 冻结 1.0 版本。冻结之后,壳就是"哑管道",任何端可独立重写而不动 engine 与 core。

## 五、插件运行时(最重要的自构件)

用户 DIY 的"源插件"(爬取/抓取在线资源)在这里运行。三个并立的设计要求:沙箱安全、全平台一份插件、普通用户写得动。

### 5.1 双引擎设计——iOS 过审的关键

| 平台 | JS 引擎 | 原因 |
|---|---|---|
| 桌面 / Android / 鸿蒙 | QuickJS(经 `rquickjs` 嵌入,~700KB) | 极小、可控、到处编译 |
| iOS | **系统 JavaScriptCore** | **App Store 审核指南 2.5.2:下载的代码只允许由 WebKit / JavaScriptCore 执行。** 用 QuickJS 跑用户下载的插件脚本 = 拒审/下架风险 |

设计含义:插件 API 面向"引擎无关的纯 JS 子集"(ES2020,无 Node API、无 DOM 全局),JS 引擎只是调度器,所有真实能力由 Rust 侧 host API 提供。引擎可整体替换,插件一字不改。

iOS 另有 B 计划(欧盟第三方商店 / 侧载分发不受 2.5.2 约束),但主路线按"能过审"设计。

### 5.2 能力式 host API + 权限 manifest

插件能触达的全部世界:

```ts
declare const host: {
  http: { get(url: string, opts?: ReqOpts): Promise<Resp> }  // 仅限 manifest 声明过的域名
  html: { parse(s: string): Doc }                            // CSS 选择器查询
  kv:   { get(k: string): string | null; set(k: string, v: string): void }  // 插件私有存储
  log:  (...args: unknown[]) => void
}
```

- 没有文件系统、没有任意域名网络、没有进程/eval。插件偷不走书库,也打不了内网。
- manifest 必填:`id` / `name` / `version` / `domains[]` / `permissions[]`,安装时逐项展示给用户确认。
- "过滤尽可能准确"的实现位置就在这里:**站点专属的 CSS 选择器规则(插件作者写)永远比通用正文提取算法准**。SDK 要把"写一个源 = 填一个搜索函数 + 一个章节解析函数"的体验做到极简。

### 5.3 中立性(承接 `4_版权与合规边界.md`)

- 内核零内置源;官方仓库只收合法白名单源(青空文库、Project Gutenberg、Royal Road、OPDS 端点等);协议与 SDK 完全开放。
- 用户从第三方装什么源是用户与第三方的事;官方不索引、不推荐、不分发侵权源。

## 六、AI 协作改变了什么、没改变什么

| | 判断 |
|---|---|
| **改变了** | 写壳、写绑定、写协议样板的成本趋近于零 → "N 个薄壳"从不可行变为可行,这是本方案敢拆壳的前提 |
| **没改变** | ① 排版引擎级复杂度(仍然不能自写);② 5 个平台的签名/打包/商店政策维护;③ 真机测试矩阵;④ 商店审核规则(2.5.2 不因 AI 而消失) |

推论:DIY 的边界画在"自包含、可单测的代码"(core / engine / 插件运行时 / 协议)与"集成与外部依赖"(渲染引擎、打包签名、商店)之间。前者放心交给 AI 大量生产,后者能买就买、能借就借。

## 七、修订路线图

v0.2–v0.4 与 `5_技术路线与MVP.md` 完全一致(阅读内核 → 本地书库 → 标注导出),仅从 v0.2 起增加 4.2 节的两条架构纪律。其后:

- **v0.5** 在线元数据与合法入口(原计划)+ **桥接协议 1.0 冻结**
- **v0.6** OPDS(原计划)
- **v0.7** 插件运行时(桌面 QuickJS 版)+ 源插件 SDK + 2 个白名单示例源
- **v0.8** Android 壳(Tauri mobile 优先,Kotlin 壳兜底)— 移动文件权限、后台下载
- **v0.9** iOS 壳 — JavaScriptCore 引擎切换 + 过审验证(2.5.2 是此版本的核心风险项)
- **v1.0+** 鸿蒙壳;Servo 桌面实验(可选,仅当系统 WebView 排版差异被证明不可忍受)

## 八、风险登记

| 风险 | 缓解 |
|---|---|
| Tauri mobile 成熟度不足 | 桥接协议使 fallback 成本 = 重写一个壳(几百行),不伤 engine/core |
| iOS 2.5.2 审核口径收紧 | JavaScriptCore 主路线 + 欧盟侧载 B 计划 |
| 各端 WebView 排版差异(尤以 WebKitGTK) | CSS 特性预算白名单 + 分页快照端到端测试 |
| FTS5 对 CJK 检索失效 | 起步即用 trigram tokenizer,不用默认 unicode61 |
| 单人精力摊薄到五端 | 桌面先行;移动按 v0.8/v0.9 排期;鸿蒙明确远期,先 PWA 兜底 |
